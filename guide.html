What Flow Lens needs

A CSV file where each row is one work item and each workflow stage has its own column containing the date the item entered that stage. Column names don't matter — you map them inside the tool.

The data stays entirely in your browser. Nothing is uploaded anywhere.

No data yet? Click Try with example data on the drop screen. It loads a fictional team dataset — all charts, tabs, and filters fully working, no setup required. Dates are always relative to today so it never looks stale.

CSV structure

The simplest possible file that works:

ID Title To do Doing Done
TKT-001Fix login bug 2026-01-102026-01-132026-01-15
TKT-002Add export button 2026-01-112026-01-14—
TKT-003Update docs 2026-01-12——

Empty cells mean the item hasn't reached that stage yet — that's expected and handled correctly.

With more stages

Add as many workflow stage columns as your process has. Items that skip stages just have an empty cell for that column.

ID Title Link Blocked Days To do Doing Ready for review Review Done

TKT-005Quick fixhttps://…0 2026-02-042026-02-04——2026-02-04

TKT-005 skipped review stages — that's fine, the tool handles it.

Column types

Required

Start stage — the first stage in your workflow (e.g. To do). Items without this date are ignored.

Required

End stage — the completion stage (e.g. Done). Items without this date are treated as work in progress.

Stage

Workflow stage columns — one per stage, containing the date entered. You need at least two for the CFD. Add as many as your process has.

Optional

ID — ticket reference. Shown in the data table and control chart tooltips.

Optional

Title — item description. Shown in tooltips.

Optional

Link — URL to the ticket in your system. Makes IDs clickable.

Optional

Blocked Days — total days the item was blocked. Used in flow efficiency and the Blocked tab. Can exceed cycle time if blocking was recorded outside your configured stage window.

Optional

Currently Blocked — a boolean flag (Yes/No, True/False, 1/0) marking whether the item is blocked right now. Separate from Blocked Days — this is a live state, not a duration. If not mapped, the Blocked tab's "currently blocked" section is unavailable.

Optional

Epic Link — the ID of the Epic (or parent) each item belongs to, e.g. COC-24768. Called Epic Link in older Jira and Parent in newer Jira. Turns on the Epic Progress tab. Map it under Epic Link in the Config panel — it is picked automatically when the column is named Epic Link or Parent, and is saved with your config. Include the Epic rows themselves in the export too, so the tab can show Epic names rather than just IDs. Items with no Epic are simply left out of that tab.

Optional

Any other column — Issue Type, Labels, Fix Version, Components, Priority, Root Cause… Used by Filters, the Release builder and the Bugs & defects setup. Multi-value cells are split into single values, whether Jira writes them as [QA, UAT] or QA|UAT.

What each tab shows

Flow Insights is your summary page. Every other tab sits in one of five menus along the top — hover or click a menu to see its tabs.

Flow Insights

Flow Insights

Your summary page: cycle time percentiles, Monte Carlo "what can we close this month?", current WIP, smelly tickets (WIP older than your 85th percentile, each showing the stage it's stuck in and ⛔ if blocked), and the Focus number — how many items were already in progress, on average, each time a new one started.

WIP & Flow menu

CFD

Cumulative Flow Diagram. Click to place a marker; place two for a range: items completed, throughput rate, WIP change per stage, and a Tickets in this range box — what Arrived (spot an influx, with the busiest day), what Reached Done, and what Moved stage, with a mix by issue type. Export the range as CSV. When you measure to a flow segment, the CFD shows just that segment's stages; the rest are struck through in the legend and come back with one click.

WIP Over Time

WIP each Monday plus a final today point (it matches the WIP card), with a 4-week average. Counts items from Active Work Starts (or Start Date if not set) until they leave. Click any point to list the tickets in progress that week — by type, by stage, how long each had been in progress, and how many are still open today.

Work Split

How your work divides across a category column such as type or priority.

Aging WIP

Every in-progress item by current stage and age, against your cycle time percentile bands. Red ring = blocked now. Items above the 85th percentile band are worth a conversation.

Arrival vs Departure

Items started vs finished each week. When arrivals keep beating departures, WIP — and cycle time — will grow.

Cycle Time menu

CT Over Time

Weekly cycle time trend. Click a week to see the items behind it.

Histogram

Cycle time distribution — where most items cluster. Min/max inputs hide outliers from the view.

Control Chart

Every finished item by finish date and cycle time, with 50/70/85/95% lines. Orange dots had blocked time.

Flow Efficiency

Share of time in active (P) stages vs queues (Q), from Start to End. A toggle includes unfinished work "so far". 100% usually means dates were entered in bulk.

Fuzzy Front End

How long items wait before the team commits to them. Needs stage columns before your Start column. More below.

Time in Stage

50% and 85% days spent in each stage. The highest is usually your bottleneck.

Throughput menu

Throughput

Items finished per week, optional normal range (XmR) and a distribution chart. Click a bar to see what was delivered.

Burn Up

Finished items climbing towards a scope target, with a straight-line forecast and faster/slower scenarios.

Epic Progress

Needs an Epic Link column. One row per Epic: progress, blocked time, pace and a forecast. Click an Epic for its stories. How pace and forecast work ↓

Releases

Your releases: progress, forecast, target dates per finish line, milestone grid and timeline, sign-off and a close-out summary. Releases & milestones ↓

Forecast

Monte Carlo — "when will N items be done?" and "how many by this date?" at 50/70/85/95% confidence.

Health menu

Team Health

This period vs the previous one: throughput, cycle time, WIP, backlog, FFE time, flow efficiency, blocked now — with traffic lights.

Blocked

Needs Blocked Days. Cycle time for blocked vs never-blocked items, items blocked now (needs Currently Blocked), and the worst offenders.

Bugs & Defects

Raised, in progress, fixed, deferred and won't fix for each type of testing work, time to fix, raised vs fixed per week, open pile over time, by fix type, and the open tickets. Bugs, defects & deferred work ↓

Breakdown

Metrics side by side for each value of a category column. Best used without slice filters.

Data

Every imported row.

Data Quality

Where every row went and any problems — dates out of order, Done before Start, items committed but not moved in 4+ weeks. Plus two information sections: Epic links (work with no Epic) and Release coverage (work not in any release, open tickets first).

How Epic Progress works out pace and forecast

Each story linked to an Epic is put in one of four groups: Done (has a Done date), In progress (reached Active Work Starts or any later stage), Committed (reached Start Date only) or Not started.

Started is the date the Epic's first story reached Active Work Starts — when real work began, not when it was committed.

Pace = stories done ÷ weeks since Started (counted as at least 1 week).

Forecast = today + (stories left ÷ pace).

Example: an Epic started on 18 Sept. On 9 Oct — 3 weeks later — 6 of its 7 stories are done. Pace = 6 ÷ 3 = 2 stories a week. One story left ÷ 2 a week = half a week, so the forecast is about 12 Oct.

The forecast only appears once an Epic has 3 or more stories done — before that it shows Too early, because one or two data points can't tell you a pace. It is a rough guide, not a promise: it assumes the team keeps the same pace on that Epic and that no new stories are added. If stories keep being added, the date will keep moving — and that in itself is worth a conversation.

Flow segments (Measure to)

A flow segment is a named Start → Finish pair inside your workflow, e.g. Code Complete (CC) = To Do → Ready for testing, or User Testing = Ready for testing → Ready to deploy. Add them in the Config panel under Flow segments, with an optional short code that appears on chips.

The Measure to pills above the charts switch every report to that segment: an item counts as finished the first day it reached the segment's finish (or any later stage), cycle time and throughput are measured to there, and work past that point stops being WIP. Flow efficiency only counts stages up to the finish. The CFD shows just that segment's stages (click a struck-through stage in its legend to bring it back). The ⓘ next to the pills lists every report affected.

Segments are how you answer "how long does it take us to get to code complete?" without changing your workflow or your data.

Releases & milestones

Building a release

  1. Click + Create a release (or Releases tab → + New release) and give it a name.
  2. Include: pick a column (Epic, Fix Version, Labels, Issue Type, any column) and tick values, or paste ticket IDs. A ticket is in if it matches any include rule.
  3. Exclude: click Exclude next to a ticket (the list keeps your place), or add an exclude rule. Excludes always win.
  4. Choose Release is done at: follow the Measure-to pill, Full flow, or a flow segment — e.g. a tranche that is judged at Code Complete. Add target dates for each finish line.
  5. Save and show reports, then Save config to keep it. If you leave the builder another way, your changes are kept and a message tells you so; only Cancel throws them away.

Using releases

  • Click a release pill and every report shows only its tickets. Click several to combine them (e.g. a tranche plus its fix-support release = everything needed for go-live).
  • Opening a release with its own finish line switches Measure to for you; going back to All work puts the pill back.
  • The release page shows the status bar (in progress split into checkpoints like Before CC / CC), blocked time, a Monte Carlo forecast on the release's own pace, the burn up, a Finish lines table (target and result for every line), the ticket list with status chips, testing work in the release, and a Jira query to check "is this what's in the release?".
  • Milestones (Releases overview): a grid of every release × finish line — ✓ reached, ○ open coloured by its chance of making the date, ● date passed — and a timeline with ◇ targets, ◆ reached dates and slip lines. The release's own finish line is outlined in purple. Click a cell to open that release measured to that line.
  • Sign-off: when the client agrees a finish line is met while a few tickets are still being refined, record the date and a note on the release page. The data isn't changed; the leftovers stay visible as "after sign-off", due by the end date.
  • Close-out: when every ticket is done, the forecast box becomes a summary — done date vs target, release lead time (first start → last finish), average cycle time per segment, flow efficiency, in-progress, queue and blocked time.

Bugs, defects & deferred work

Tell Flow Lens what testing work looks like

Config panel → Bugs & defects. Each type (e.g. Bug (internal) from your QA team, Defect (external) from testers) is a set of rules on any columns. Click the word between rules to switch and (every rule must match — Issue Type = Task and Labels = QA) or or (any rule — Issue Type = Task or Labels = TestingDeepDive). A ticket that matches two types counts under the first. Optionally pick a Fix type column (Root Cause, Fix Type…).

What you get

  • Testing work: Include / Hide / Only — a switch under the release pills that every report follows. Hide = flow metrics for feature work only; Only = how long fixes take. It tells you when a filter or release already leaves testing work out.
  • Bugs & Defects report: Raised (not started) · In progress · Fixed · Deferred · Won't fix per type; time to fix (50% / 85%); oldest open; "last 4 weeks: X raised, Y fixed — open pile growing / shrinking"; raised vs fixed per week; open at the end of each week; by fix type; and the open tickets. The fix-type table and ticket list are boxes you can close — closed boxes are left out of snapshots.
  • On a release page: a "Testing work" line and a Bug / Defect tag on each ticket.

Deferred to future work (change requests)

Moving a ticket back to Backlog in Jira isn't enough — the export keeps its old stage dates, so it still looks in progress. Add a label instead (e.g. CR-Needed; Jira labels can't have spaces) and set the Deferred rule to it. Deferred tickets leave WIP, throughput, forecasts and the release's remaining work, but stay visible as Deferred on releases, Epics and the Bugs & Defects report. It works for any ticket, not just bugs.

For bugs to count against a release, link them to the release's Epics (or give them its Fix Version) in Jira. Otherwise the release page shows no testing work — Data Quality → Release coverage lists what's outside every release.

Snapshots

Copy puts an image of the current tab on your clipboard, sized for email and Teams (about 1,000px wide). Save image saves a full-resolution PNG for slides and print. Both show every row of long lists, and a footer with the release, Measure to, testing switch and filters, so nobody mistakes a filtered view for the whole picture. Closed boxes (fix type, ticket lists, tickets-in-range, WIP list) are left out — close what you don't want to send.

How the numbers are worked out

  • Cycle time = Start → End (or the segment's start → finish). Every from → to span is a cycle time; the span is shown under the number. Only a finished release's first-start → last-finish is called release lead time.
  • WIP = from Active Work Starts (else Start) until the item leaves — done, discarded or deferred. The WIP card, WIP Over Time and the Focus number all use this.
  • Throughput = items finished per Monday-to-Sunday week, empty weeks included, from the first finish to the latest date in your file. Every forecast uses this.
  • Flow efficiency = time in P stages ÷ total time from Start to End, minus blocked days.
  • Forecasts (Monte Carlo) replay your real weekly throughput thousands of times. A release forecast uses the release's own pace (needs 3+ done).

Fuzzy Front End and the commitment point

The commitment point is the moment the team commits to doing the work — typically a "Ready" or "Selected" stage. In Flow Lens, this is your Start column.

Cycle time is measured from the commitment point to Done. It represents the customer's wait time once the team has accepted the work.

Everything before the commitment point is the Fuzzy Front End (FFE) — the time an idea spends being created, discussed, refined, and prioritised before the team commits to it. This is not part of cycle time.

How Flow Lens handles this

Any workflow stage columns ordered before your Start column are automatically treated as backlog. You don't need to configure anything separately — the order you set in the Config panel is all that matters.

For example, if your stages are:

Idea Refine Ready ← Start Doing Done
← FFE (backlog) ← cycle time measured here

Idea and Refine are FFE. The Fuzzy Front End tab shows how long items spend here before being committed.

If you don't have pre-start stages

If your CSV only has stages from the commitment point onwards (e.g. To do, Doing, Done), the FFE tab and Team Health backlog metrics will show a blank state. That's expected — there's simply no pre-commitment data to analyse.

FFE time is measured from the earliest date in any pre-start stage to the date the item entered your Start column.

A note on "Ready"

Some teams debate whether "Ready" is the commitment point or still part of the queue. In Flow Lens, Ready (your Start column) is the commitment point — cycle time starts here. Items sitting in Ready waiting to be picked up are counted as committed WIP, not backlog. This is the stricter interpretation and the one that keeps cycle time honest.

Setting up the tool

  1. Drop your CSV onto the tool. It will detect date columns automatically.
  2. In the Config panel, map your columns: set Start, End, and optionally Active Work Starts, ID, Title, Link, Blocked Days, Currently Blocked and Epic Link.
  3. Drag the workflow stage rows into the correct order — left to right, earliest to latest.
  4. Set each stage's type with its button: P process, Q queue, X discarded (e.g. Cancelled, Withdrawn, Not done). More on discarded stages ↓
  5. Optional: add flow segments, bugs & defects types, and build releases.
  6. The charts update immediately. Use Filters (e.g. hide Issue Type = Epic) and the date range to focus.
  7. Click Save config to keep your setup as a small JSON file — the ● Unsaved changes marker and a one-off popup tell you when there's something to save. Next time, drop in the new CSV and click Load config; a message lists what the file holds and warns about any column the new file doesn't have.

If your export gains a new stage column (say you start capturing Withdrawn), just load your old config. Your saved settings are applied and the new column is added to the workflow with a note asking you to check its type. Then Save config again to keep it.

Tips and gotchas

Cancelled / rejected items — mark them Discarded (X)

Each stage in the Config stage list has a type button. Click it to cycle through:

  • P — Process: active work (Dev, Testing). Counts as work time in flow efficiency.
  • Q — Queue: waiting (Ready for Dev, Awaiting Deploy). Counts as wait time.
  • X — Discarded: the item left without being delivered (Rejected, Cancelled, Withdrawn, Not done, Won't do). Picked automatically for stages with those kinds of names.

A discarded item stops being WIP or backlog on the date it was discarded, but it is never counted as delivered — it is left out of throughput, cycle time, forecasts and Burn Up scope. You'll see discarded items as their own band at the bottom of the CFD, a dashed "Discarded" line on Arrival vs Departure, a "Discarded" row on the Data Quality tab, and "+N discarded" on Epic Progress.

You no longer need to filter cancelled items out of your data. Filtering removes their history — they really were in progress until they were cancelled. Marking the stage X keeps WIP over time accurate. If an item has both a Done date and a Discarded date (export tools fill in every stage an item passes through), whichever column comes later in your file wins — so it works whether your export puts Withdrawn before or after Done.

Items that skip stages

Common and expected. Leave the cell empty — the tool handles this correctly in all charts including the CFD.

Zero cycle time

If many items show 0-day cycle time, your start and end date columns contain the same date in the source data. The histogram will show an empty state — this is correct, not a bug.

Stage ordering matters for the CFD

Drag stages into the correct process order in the Config panel. The CFD is built from that order — wrong order produces meaningless bands.

Bulk moves in Jira

Moving lots of tickets several stages in one go (e.g. closing 40 stories after an agreed sign-off) shows up as a cliff on the CFD and WIP charts, a one-week throughput spike that makes forecasts too optimistic for a few weeks, and near-zero time in the stages they skipped. Set a release's finish line to where the real work ended, and treat team throughput with care until that week drops out of the window.

When a CFD isn't the right chart

CFDs shine for a whole team over months. For a small release or tranche, the release page, Aging WIP and the milestone grid usually answer the question better — small batches make blocky CFDs.
